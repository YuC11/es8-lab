# 逐关重构执行计划

> 状态：待实施计划。范围为现有 44 关的教学闭环重构，不预设每关都要加长正文。基线来自 `backend/src/main/resources/knowledge/modules.json`、`backend/src/main/java/com/eslab/levels/`、`front/src/lib/levelCalls.ts`、`docs/关卡.md` 与 `docs/覆盖率评估.md`。每项完成后再更新该关的知识文案、请求清单、Java 实现及相关文档。

## 目标与统一完成定义

把每关从“说明概念 + 一次性跑完”调整为可观察、可比较、可复现的微型实验。每关至少具备：

1. **问题与假设**：把目标改成可验证问题；给出运行前预测，但不评分。
2. **基线和对照**：明确只改变哪个变量；数据集、查询条件、规模、刷新状态等保持一致。
3. **分步动作**：运行前状态、核心请求、对照请求、清理/恢复步骤；破坏性步骤写明影响范围。
4. **证据**：返回原始 ES 响应，并从中提取可核对指标；性能结论用多轮中位数，非性能结论给命中、mapping、计数或错误响应等结构证据。
5. **解释边界**：写出本机单节点/小数据的局限、可能混淆变量和不应外推的结论。
6. **迁移练习**：至少一条 probe 改变一个参数，让学习者说明结果为何变化；有可逆状态的关卡必须附复位方式。

每一关的“完成”定义：知识库中的 `objective / predict / steps / takeaway / pitfall / probes` 与源码实现一致；`levelCalls.ts` 列出的请求与真实执行顺序一致；页面能展示关键原始证据；清理后重跑可复现。实现时遵守架构边界：ES 请求仅通过 `EsClient`，数据集只由 `DatasetService` 管，实验索引用 `LabData` 并限于 `eslab-*`。

## 优先级与批次

- **P0：证据可信度**：m3-2、m6-2、m6-3、m7-1、m7-2。先修方法学和结论口径，避免后续内容建立在误导性数字上。
- **P1：基础概念闭环**：M0–M5。逐关补齐前置状态、对照和结果解释，形成稳定的索引、写入、查询、聚合路径。
- **P2：查询体验与运行机制**：M6–M9。确保分页、诊断、搜索相关性与零停机操作的证据可复核。
- **P3：写入治理与索引工厂**：M10–M11。补齐错误分支、幂等与清理，强化生产决策迁移。

建议每批按“盘点 → 改知识 JSON → 改 Java → 同步 levelCalls → 页面核对 → 更新关卡清单”执行；不要同一提交同时重写多关的实验数据模型。

## 横向工程任务

1. **统一实验结果模型**：在现有 `LevelResult` 的基础上承载样本表、原始响应、口径说明和限制；不把实验数据塞进文案字符串。
2. **统一清理策略**：每关定义仅限自身的索引/别名/PIT/task/模板/pipeline 资源；必要时在失败和异常路径清理，避免误删其他实验。
3. **前后端请求清单校验**：每次改关卡 API 请求同步更新 `front/src/lib/levelCalls.ts`；验收时逐项比较 path/method/body 与 Java 实际请求。
4. **教学证据来源**：静态数字标为“典型基线”并注明环境；动态结果必须来自当前 ES 响应，不能用文档预置值伪装测量。
5. **课程索引联动**：同步更新 `docs/关卡.md`、必要时 `docs/实验.md` 与覆盖率评估；保留历史基线时明确日期和评分口径。

## M1–M6 核心操作小关卡扩展

### 扩展原则

当前 44 关已覆盖多个概念，但“介绍某类 DSL”不等于覆盖了 Elasticsearch 日常基本操作。新增内容要按**可完成的操作任务**拆关，而不是把更多 API 名称塞进现有关卡。新增关卡保持与现有课程一致：真请求、真响应、源码可读、前置条件清晰；每关只引入一个主要变量。新关卡暂不计入 44 关，实施后统一更新章节编号、前置依赖与覆盖率口径。

| m1-6 | M1 末 | Mapping 与 settings 现场巡检 | `GET /_mapping`、`GET /_settings`、`_field_caps`；对比 v1/v2 同字段能力 | 类型、analyzer、doc_values、searchable/aggregatable；指出不可变与可动态更新设置 |
| m2-3 | M2 末 | 用 `_analyze` 调试查询为什么没命中 | 对字段 analyzer 与显式 analyzer 跑相同输入；比较 token、position、offset | token 差异能够解释指定 query 的召回差异；插件缺失有清晰前置错误 |
| m3-4 | M3 末 | Bulk 失败处理：逐项错误、重试与幂等 | bulk 混合成功/故意失败动作；修正后重放；对比 `index` 与 `create` | HTTP 200 但 `errors=true` 的逐项状态；成功/失败数；安全重试条件 |
| m4-7 | M4 末 | 查询结果控制：`_source`、`docvalue_fields`、`stored_fields` | 同一查询改变返回字段方式；读回 mapping 存储能力 | 返回体差异与字段可取性；解释少取字段对传输量的意义，不声称改变命中集 |
| m4-8 | M4 末 | 多请求查询：`_msearch` 与 `_mget` | 等价的多次 `_search` vs 一次 `_msearch`；逐 id GET vs `_mget` | 子响应与输入顺序对应、单项失败隔离；请求数和正确性对照，性能不做单轮结论 |
| m5-4 | M5 末 | 常用指标聚合：filter/range/cardinality | 同一过滤集合下做 `filter`、`range`、`cardinality`；与精确去重样本核对 | bucket 边界、doc_count、基数近似误差；不给 HyperLogLog++ 近似值贴精确标签 |
| m5-5 | M5 末 | 大桶遍历：composite aggregation | 用 `after_key` 分页遍历所有 bucket，与 terms top-N 比较 | 页间无重复/遗漏的 key 检查、桶总量；解释 composite 是遍历而非排序全部文档 |
| m6-4 | M6 末 | Scroll 导出与 PIT 分页的适用边界 | 固定样本跑 scroll 批量遍历，并对照 PIT + `search_after`；显式清理上下文 | 遍历总数/重复数、上下文关闭、过期行为；给出批量导出与交互翻页的选择规则 |
| m6-5 | M6 末 | Explain：单文档相关性逐项诊断 | 对同一文档运行 `_explain`，改一个 query 子句对照；与 search `_score` 对齐 | explanation 树、匹配/不匹配原因、score 对照；注明 explain 是单文档诊断且有额外成本 |

**后续候选，不纳入本轮核心小关卡承诺**：fuzzy、nested 查询、geo、ES|QL、向量检索。只有当索引模型、8.18.5 API 支持和教学目标已验证后才排期；不得为了“覆盖面”直接往 v1/v2 塞字段。

### 整体索引策略判断

现有索引职责：`eslab-products-v1/v2` 是 20 万商品主教材索引；`eslab-goods-*` 是后续关卡可重建的实验索引，`LabData` 对写入名做前缀校验。新增知识应首先判断能否在这两种职责内安全实现。

| 内容 | 推荐承载方式 | 是否改主索引 | 判断依据 |
|---|---|---|---|
| CRUD、mapping/settings 巡检、bulk 错误、`_msearch`/`_mget`、source filtering、常规查询/聚合、scroll/PIT/explain | 复用 v1/v2 只读对照，或用小型 `eslab-goods-core-*` 可重建样例 | 通常不需要 | 属于 API 操作能力，不必污染主商品 mapping；会写入/删除的操作应落在独立实验索引 |
| 新增商品普通字段，且可由当前 Generator 稳定生成、后续多章会复用 | 同步扩展 v1/v2 mapping 与 `ProductDoc`，迁移通过删建/seed 完成 | 可以，但需版本化评估 | 字段若成为长期公共课程素材，两个主索引都应有明确一致的语义；动态 v1 与显式 v2 的设计差异保留 |
| `nested` 数组关联、geo 坐标、dense_vector 等具有专门类型/查询语义的数据 | 建独立 `eslab-goods-nested-*` / `geo-*` / `vector-*` 教学索引 | 不应 | 特殊 mapping 会改变主索引结构；向量需要真实 embedding 来源，合成向量只能演示 API 机制，不能支持检索质量结论 |
| 仅用于模板、pipeline、同义词、rollover 或删除/冲突演示的状态 | 继续使用独立 `eslab-goods-*` 实验资源，并定义 cleanup/re-run | 不应 | 状态具有生命周期或破坏性，不应依赖学员主数据当前状态 |

**结论**：本轮默认不变更 `eslab-products-v1/v2` 主索引。先在 `LabData` 增加小型、确定性、可幂等重建的 core 样例数据；仅当多个关卡都需要的新字段确立为课程公共 schema 后，才升级主索引定义并提供明确重建路径。允许变更索引不等于应当改全部索引。每次变更列明索引名、mapping 变动、文档生成方式、前置依赖、清理和旧数据兼容性。

### 新增关卡的实施步骤与验收

1. 先为每个候选 ID 定义唯一学习目标和前置关卡，确认不会与现有关卡重复。
2. 设计并实现小型实验数据集；`LabData` 统一定义创建/填充/清理，任何写操作限制在 `eslab-goods-*`。
3. 增加 Java `LevelModule` 实现，响应必须包含可核验结果和原始 ES 响应；处理部分失败、重复运行及异常清理。
4. 在 `modules.json` 增加关卡内容，并同步 `LevelRegistry`、`levelCalls.ts`、课程导航、关卡清单与前置依赖。
5. 对涉及管理/写入 API 的操作更新 `/api/console` 白名单与 body 校验；仅新增最窄的 `eslab-*` 范围能力。
6. 逐关从空实验索引运行两次，再清理重跑；核对关卡输出、ES 实际状态和请求清单一致。

完成判定：计划中的十个核心小关卡均已实现，或有逐项说明的延期决定；所有新增索引有生命周期说明；v1/v2 无非必要 mapping 变更；课程总数和覆盖率数据已同步更新。
