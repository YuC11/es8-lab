# 覆盖率评估

评估对象：本仓库的 27 关课程。评估时间：2026-11-05。

> **本文件是补齐前的基线，保留原文不改。** 按第十节的路线补完 M8 / M9 / M10 / M11 四章后（27 关 → 44 关），三个口径已重算，见文末[第十三节](#十三补齐后重算44-关)。

结论先行：**基础设施层 90%，产品能力层 8%。** 它把「ES 内部怎么运转」讲透了，把「搜索产品怎么对用户负责、上线后怎么活下去」留空了。

## 一、总览

| 口径 | 项数 | 得分 | 覆盖率 |
|---|---|---|---|
| A 商品搜索全链路 | 18 | 30 / 54 | **56%** |
| B 生产上线 checklist | 20 | 24 / 60 | **40%** |
| C ES 能力全景 | 36 | 40 / 108 | **37%** |

三个数都对，取决于你拿它干什么：A 回答「照这个场景够不够」；B 回答「能不能上线」；C 回答「在 ES 里算什么水平」。

## 二、评分标准

每项 0-3 分，避免二元判断把「能跑出数字」的教学与「只提了一句」拉平。

| 分 | 含义 |
|---|---|
| 0 | 未讲 |
| 1 | 只讲概念（文案提及，没有可执行请求） |
| 2 | 有可执行请求（控制台或 probe 能跑出真数字） |
| 3 | 独立关卡 + 实测结论 + 源码可读 |

覆盖率 = Σ得分 ÷ (项数 × 3)，等权，不加主观权重。

## 三、分层：真正的断层

| 层 | 覆盖 | 典型内容 |
|---|---|---|
| **基础设施层** | **90%** | 建库、Mapping、分词、写入、基础查询、分页、性能诊断 |
| 查询进阶层 | 8% | multi_match、match_phrase、fuzzy、function_score |
| 搜索体验层 | 11% | highlight、suggest、completion |
| 运维安全层 | 22% | alias、模板、ILM、快照、安全、监控 |
| 建模进阶层 | 17% | nested、geo、自定义 analyzer、dynamic_templates |
| 新兴能力层 | 0% | 向量检索、语义检索、ES\|QL |

90% 与 8% 的落差不是「讲得不够多」，是**内容结构决定的**：前 5 章都在讲「数据怎么进去、怎么被找到」，第 6-7 章讲「怎么查得快」，没有任何一章讲「用户搜不到想要的怎么办」。

## 七、判低：被 0-3 分制压缩的宽项

初版评分按「API 有没有被调用」判定，把这些记成了 0。它们实际在文案里出现过，应记 1：

`reindex`、`nested`、`force merge`、`composite agg`、`scroll`、`index template`、`同义词`。

但更重要的是另一类压缩：**有些关卡一个顶好几个知识点，按一项计分会低估**。

- **m1-2** 一关里含 7 个 Mapping 决策：`scaled_float(100)`、`half_float`、`ignore_above: 256`、keyword 多字段、`ik_max_word` + `ik_smart` 双分词、`dynamic: strict`、`object` 而非 nested。记 1 项 3 分，等于把这 7 个压成 1 个。
- **写入路径**是 3 关 + 1 个实验（m0-4、m3-1、m3-2、m3-3、exp-refresh-bulk），不只是「bulk 一项」。
- **m4-5** 用「命中数 + max_score」两个口径证明参数分两类，比「支持 term/match/range」深一层。
- **m5-1** 讲的是「报表数字为什么不准」（`doc_count_error_upper_bound` + `shard_size` 对照），不是「terms 怎么写」。

所以 37% 是偏保守的下界。若把这些宽项拆开，口径 C 会到 45% 左右。

## 八、判高：四个数字支撑不住结论

这四关有独立关卡、有实测、有源码，按标准应记 3。但**数字的因果归因不成立**，建议压到 2。

| 关卡 | 问题 |
|---|---|
| **m7-1 分片规划** | v1 与 v2 同时变了分片数、Mapping、分词器、doc_values。体积 88MB→63MB、耗时差，**无法归因到分片数**。20 万规模下每个分片只有约 21MB，远低于它自己写的 10–50GB 区间，结论只能是「本规模看不出」 |
| **m6-3 profile** | `walkProfile` 把每个节点的 `time_in_nanos` 都累加再递归子节点，父节点时间本来已含子节点，**重复计数**；且只遍历 query 阶段，没有 fetch。所以「query 阶段累计 19ms」既不是单次真实耗时，也不是阶段拆分 |
| **m6-2 search_after** | 只测 10 页总墙钟再除以 10。「与页深无关」是断言，不是实测 —— 没有记录逐页耗时，也没有在 from=0 与 from=100k 两个起点各翻 10 页对照 |
| **m3-2 _id 策略** | 单轮采样 + 毫秒整数差 + 分母钳到 `0.0001`。auto 组 delta=0 时，biz 组稍有耗时就会算出 10×/100× 的假结论 |

共同点：**方法学是讲究的（多轮取中位数、有预热、结论写明口径边界），但对照变量没有控制住**。这类问题比「没讲」更需要警惕，因为它看起来已经覆盖了。

## 十、补齐路线（按 ROI 排序）

ROI = 对「能独立上线一个商品搜索」的帮助 ÷ 实现成本。不可演示的部分按比例放大成本。

| # | 方案 | 关卡 | 新增 API | 可演示 | ROI |
|---|---|---|---|---|---|
| 1 | **索引变更与零停机** | 3-4 | `_aliases` · `_reindex` · `_tasks` · `_forcemerge` · `_rollover` | 全部 | **3.3** |
| 2 | **索引工厂与数据接入** | 3 | `_index_template` · `_simulate` · `dynamic_templates` · `flattened` · `_ingest/pipeline` | 全部 | 2.5 |
| 3 | **增量写入与并发** | 3-4 | `_update` · `if_seq_no` · `_bulk` 的 update/delete · `_update_by_query` | 全部 | 2.25 |
| 4 | **相关性工程与搜索体验** | 4-6 | multi_match · match_phrase · function_score · collapse · highlight · suggest · synonym_graph · nested | 全部（零白名单改动） | 1.67 |
| 补丁 | ES\|QL + `_msearch`/`_mget` | 2 | `_query` · `_msearch` · `_mget` | 全部 | 高 |
| 补丁 | 五个最常用查询 | 2-3 | multi_match · phrase · function_score · highlight · suggest | 全部 | 高 |

**为什么第 1 是索引变更**：没有 alias，任何 mapping 变更都要停机 —— 这是上线阻塞项，且成本最低。

**为什么第 4 最重要却排第 4**：它决定「商品搜索之所以是商品搜索」，但要新建 demo 索引、要 4-6 关，成本最高所以 ROI 被摊薄。**先做 1，紧跟 4。**

## 十一、明确不做

平台约束是「每关必须跑出真数字」。以下能力在单节点本地环境无法真实演示，做成关卡会让边际教学价值趋近于零：

| 能力 | 不能跑的原因 |
|---|---|
| snapshot / SLM | 需 `path.repo` 并重启 ES |
| CCR / 跨集群搜索 | 需 2 个集群 + license |
| RBAC / TLS | 需开启 security + 证书，会破坏平台与 ES 的连接 |
| ILM 的 warm / cold / frozen 迁移 | 单节点无多 tier，迁移不可观测 |
| 副本故障转移 / 跨可用区 | 单节点 |

替代方案：做成一个参考页《上线前必须知道的 10 件事》，每项给「验证命令 + 预期输出 + 为什么本机演示不了」。比 3 个点了不出数的关卡更有价值。

## 十二、怎么复算

1. 按第二节的 0-3 分制，对第四至六节的任一项核对：这个能力有没有独立关卡？关卡里有没有实测数字？有没有源码可读？
2. 覆盖率 = 得分和 ÷ (项数 × 3)。
3. 分层数字来自第六节的 36 项按层的分组求和。

分歧最大的通常是「只讲概念」算 1 还是 0。本表一律算 1 —— 如果算 0，口径 C 会从 37% 降到 30%，口径 B 从 40% 降到 32%。

## 十六、m6-2 / m6-3 的测量方法改掉后重算（2026-11-06 第四批）

这两关此前不是「没内容」，而是「测量方式撑不住结论」，所以在覆盖率里各按 2 分记。这一轮把方法改掉，
结论也随之变窄 —— 换来的是「表格里的每个数字都能指到一条请求」。

| 关卡 | 改之前 | 改之后（本机实测） |
|---|---|---|
| m6-2 | 只记 10 页总墙钟，「每页代价恒定」是断言 | 同一 PIT 内从第 1 / 51 / 100 页各翻 4 页，逐页记录每片候选量（100 / 5,100 / 10,000）、`took` 与末条游标；定位 `took` 2 → 4 → 4ms，游标页恒 1–2ms；`from=15000` 抓到 400（root_cause：Result window 15100 > 10000）；关闭 PIT 后 `num_freed=3`、`open_contexts` 回到基线、旧 id 复用 404 |
| m6-3 | 只取 profile 根节点按类型累加，fetch 段根本没读 | 树按父子展开，每节点两列：累计（含子节点）与自身（累计 − 子节点）；query / collector / fetch 三段分列（`fetch` 在 `shards[].fetch`，不在 `searches[]`）；`took` 单列 16ms，query 合计 6.76ms、collector 0.65ms、fetch 1.04ms；最贵的自身耗时是 price 的 `IndexOrDocValuesQuery` |

### 分数变化

| 口径 | 第十五节 | 本节 | 来源 |
|---|---|---|---|
| A 商品搜索全链路（18 项 / 54 分） | 51 · 94% | 51 · **94%** | 无变化：这两关属 C 口径 |
| B 生产上线 checklist（20 项 / 60 分） | 39 · 65% | 39 · **65%** | 无变化 |
| C ES 能力全景（36 项 / 108 分） | 73 · 68% | 74 · **69%** | 「profile 定位慢查询」2→3 |

### 这一轮换来的是什么边界

- **2 万条 / 3 分片下，from 的代价只有几毫秒**，而 `took` 的分辨率是 1ms。所以表格里「51 页比 100 页贵 1ms」
  这种反序是量化噪声，关卡里直接写「不要读成曲线」。能确定的是两件硬事实：每片候选量 = from+size、
  以及超过窗口直接 400。
- **客户端墙钟的固定开销约 4ms，比要测的差异还大**。第一次实现用墙钟对比，结论是「深翻不花钱」——
  完全反了。现在两列并排给出，结论只取 `took`，这个坑本身也写进了关卡 notes。
- **profile 单次抖动大**，只用来定位热点（谁最贵、贵在哪个阶段），不做基准；要比较优化前后必须多轮采样。
- 这两关仍然证明不了「线上会慢几倍」：数据量、分片数、查询成本都会改变斜率。覆盖率给 3 分是因为
  「方法可复核、结论有边界」，不是因为它给出了可外推的性能数字。
